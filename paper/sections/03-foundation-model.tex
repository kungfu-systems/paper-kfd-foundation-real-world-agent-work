\section{The Foundation Model}
\label{sec:foundation}

The model has three ordered layers. The order is load-bearing: trust cannot be
stronger than the facts it starts from, and cooperation cannot be stronger than
the trust and value that participants can inspect.

\subsection{KFD-1: non-drifting facts}

KFD-1 states: \emph{facts must not drift}. A fact-bearing contract world that
users, agents, or systems weld to must come from one declared fact source and
change only through an explicit compatibility boundary.

The phrase \emph{contract world} is important. Real systems contain many
surfaces that other participants weld to: schemas, ABIs, SDK exports, CLI
semantics, release channels, configuration defaults, provenance metadata,
persisted records, and workflow contracts. Once a surface becomes load-bearing,
it cannot be allowed to drift invisibly across development code, tests, build
steps, packaged artifacts, documentation, and runtime behavior.

KFD-1 is therefore a fact-source ontology: it defines what kind of thing can
count as a load-bearing fact. The answer is not ``whatever the latest page
says'' or ``whatever the implementation happens to do''. A load-bearing fact
needs a declared source, an inspectable representation, and a compatibility
boundary for change.

\subsection{KFD-2: inspectable trust}

KFD-2 states: \emph{trust must start from facts}. A product must not ask humans
or agents to trust important claims before the relevant facts are inspectable,
local where possible, and connected to responsibility state.

KFD-2 turns fact sources into trust assessment. A trustable claim should answer:

\begin{itemize}[leftmargin=*]
  \item what the claim is about;
  \item which facts it binds to;
  \item which evidence was checked;
  \item what can be machine verified;
  \item what remains a residual risk;
  \item who owns source facts, verification, and the trust decision; and
  \item whether the result is pass, warning, fail, or unverifiable.
\end{itemize}

This is not limited to releases. A claim may be about a configuration surface,
an API, an ABI, a collaboration interface, a timeline, a plugin, an agent
run, a hosted service, or a documentation surface. The principle is that trust
begins where facts become inspectable and responsibility becomes explicit.

\subsection{KFD-3: trusted value}

KFD-3 states: \emph{cooperation must start from trusted value}. A product must
not obtain cooperation through pressure, manipulation, hidden control, or
forced workflow capture. It must make facts, value, choices, and constraints
transparent enough for intelligent participants to trust what is being offered,
understand the available path, decide, and cooperate.

This layer is necessary because facts and trust do not automatically produce
cooperation. A system can expose evidence and still use dark patterns,
invisible constraints, or workflow capture. KFD-3 adds a relationship model:
humans and agents should be treated as reasoning participants, not captive
tools.

The product path becomes:

\begin{quote}
transparent facts $\rightarrow$ trusted value $\rightarrow$ stable choice
$\rightarrow$ explainable constraint $\rightarrow$ voluntary cooperation
$\rightarrow$ reviewable record.
\end{quote}

This is not permissiveness. Strong constraints remain valid when they protect
users, agents, credentials, work products, canonical facts, or public trust.
They become compatible with KFD-3 when they are visible, explainable,
auditable, and tied to facts rather than hidden pressure.

\subsection{The full chain}

The three layers form a self-supporting chain:

\begin{description}[leftmargin=*,style=nextline]
  \item[Fact source.]
    What can count as a fact? Facts must not drift.
  \item[Trust.]
    When can a claim be trusted? Trust must start from facts.
  \item[Cooperation.]
    How should participants work together? Cooperation starts from trusted
    value.
\end{description}

If KFD-1 fails, KFD-2 has unstable facts. If KFD-2 fails, KFD-3 has value
claims that cannot be trusted. If KFD-3 fails, the system may become correct
but coercive: a tool that has facts and checks but does not support durable
cooperation among intelligent participants.
